# MiniCode · 轻量级 Coding Agent（v2）

> 在 project1 网关「韧性调用」模式之上，实现 Coding Agent 的 Planner-Action-Observation 循环，
> 并在 v2 中解决了 v1 发现的**幻觉式汇报**问题：把「用事实判定」这条原则内建进 Agent 循环。

## 核心结论（30 个 bug 用例 × 2 次独立实测，见 `results/eval_*.md`）

| 配置 | 自愈成功率 | **幻觉式汇报率** | 平均轮数 | 平均 token/任务 |
|---|---|---|---|---|
| v1 行为（无结果校验） | **77%**（两次一致） | **17% ~ 23%** | 4.20 ~ 4.37 | 2912 ~ 3184 |
| **v2（启用结果校验）** | **87% ~ 93%** | **3% ~ 7%** | 4.40 ~ 4.63 | 3329 ~ 3483 |

**为什么给区间而不是单个数字**：模型温度已调到 0.2，但输出仍不确定。
所以 A/B 各跑了两遍（每遍 30 例），报区间而不是挑一个好看的数——
报单点数字在面试里经不起"你跑了几次"的追问。

**代价**：平均多 0.2~0.4 轮、多 ~400 token（+13%）。
**收益**：幻觉率下降约 **16 个百分点（降幅约 75%）**，成功率提升 **10~16 个百分点**。

## v2 做了什么

### 1. 结果校验步骤（核心改进）

v1 的实测发现：**5 个 case 里有 2 个，Agent 全程没报失败，最后宣称"已修复"，但实际没修对。**
也就是 40% 的幻觉式汇报率。v1 只能靠人工事后判定，Agent 自己完全不知情。

v2 把"用事实判定"内建进 Agent 循环：

```
模型想输出 final
     │
     ├─ v1：直接采信 ← 幻觉的来源
     │
     └─ v2：先验事实
          ├─ verifier 通过 → 采信 final
          └─ verifier 不通过 → 把「实际输出 vs 期望输出」喂回模型 → 继续修
```

关键设计：

- **verifier 与评测器分离**：循环内的 verifier 负责"给它反馈让它自愈"；
  循环结束后的独立 judge 负责"统计成功率与幻觉率"。两者独立，**避免自己判自己及格**。
- **fail-closed**：verifier 自身抛异常时按"未通过"处理，绝不放行
  （见 `test_verifier_exception_does_not_crash`）。
- **不用 `success` 当真相**：`AgentResult` 上刻意**不提供** `hallucinated` 属性。
  Agent 没有独立于自己的判定器，不可能知道事实真相——真相只由评测器给出。
  （这个设计避免了"用 success 自证清白"的循环论证。）

### 2. 基准集从 5 例扩到 30 例

v1 只有 5 个 case，样本量太小，任何结论都是观察性的。v2 按难度分 5 类各 6 例：

| 类别 | 说明 | 例数 |
|---|---|---|
| `syntax` | 语法错误——stderr 直接指明，最容易 | 6 |
| `runtime` | 运行时异常——需正确理解异常信息 | 6 |
| `logic` | **逻辑错误（不报错但结果错）**——最考验意图理解 | 6 |
| `dependency` | 依赖/接口错误——调用不存在或用错 API | 6 |
| `boundary` | 边界条件——空、除零、负数、极端输入 | 6 |

### 3. Trace + token 成本记账

`app/trace.py` 记录每一步的 action / 参数 / 耗时 / token / 观察结果，
评测器为每个用例自动落 trace 到 `results/traces/`。
没有 trace，"它为什么修错了"永远说不清；没有 token 记账，"换个模型划不划算"无法回答。

## 分维度结论：哪类能修、哪类修不了

以启用结果校验的两次实测汇总：

| 类别 | 无校验成功率 | **启用校验** | 关键观察 |
|---|---|---|---|
| `syntax` | 100% | **100%** | stderr 已经把答案写脸上，校验器帮不上忙 |
| `runtime` | 50% | **83% ~ 100%** | 校验器把"消掉报错但语义错"挡掉不少 |
| `logic` | 50% | **33% ~ 83%** | 波动最大的一类，见下 |
| `dependency` | 83% | **100%** | 校验器几乎能兜住这一类 |
| `boundary` | 100% | **100%** | 任务描述里给了期望输出，等于给了答案 |

**最重要的发现**：`logic`（逻辑错误）是两种模型共同的天花板——
它不报语法错，模型倾向于"用最小改动消掉症状"而不是理解意图：

- `runtime_index_error`：期望输出 5，模型把越界改成"返回最后一个元素"拿到 3
- `logic_wrong_return`：期望"中间两元素之和"，模型改出 `nums[1]+nums[2]` 越界

**这说明「不报错但结果错」的问题，靠让模型自查是补不上的，必须用外部事实验证器兜底。**
而校验器对 `logic` 也有天花板——它只能告诉模型"输出不对"，不能告诉它"你为什么想错了"。

## 跨模型对比：模型能力是 Agent 的上限

同一套 30 例基准、同一套 harness（均启用结果校验）：

| 模型 | 成功率 | 幻觉率 | 宣称完成率 | 平均轮数 | 平均 token | 平均耗时 |
|---|---|---|---|---|---|---|
| `Qwen/Qwen2.5-7B-Instruct` | 87% ~ 93% | 3% ~ 7% | 100% | 4.4 ~ 4.6 | 3329 ~ 3483 | **9.1s** |
| `deepseek-ai/DeepSeek-V3` | 87% | **0%** | 80% | 4.6 | 4483 | **1255.1s** ⚠️ |

两个值得讲的发现：

1. **DeepSeek-V3 的幻觉率为 0%，且"宣称完成率"只有 80%**——
   剩下 20% 它**没有假装完成**，而是跑满轮数后如实报告未完成。
   这说明"诚实度"不只取决于校验器，也取决于模型本身的行为倾向。
2. **⚠️ DeepSeek-V3 平均 1255s/任务，比 7B 慢两个数量级**，
   疑似免费档限流排队。**这组数字不宜与 7B 直接横向比较**——
   它同时也暴露了另一个工程事实：跨模型对比时，**上游的限流策略会污染延迟指标**，
   必须把"耗时离群"当成数据质量问题单独标出来，而不是当结论。

## 怎么跑

```bash
python -m eval.runner --ab                             # A/B 对照（开关结果校验）
python -m eval.runner --models deepseek-ai/DeepSeek-V3 # 跨模型对比
python -m eval.runner --per-category 1                  # 每类 1 例快速冒烟
python -m eval.runner --models X --no-verify           # 复现 v1 行为
```

结果写入 `results/eval_<时间戳>.{md,json}`，逐例 trace 写入 `results/traces/`。
评测带**断点续跑**（每例结果实时落 jsonl），中断不会丢已完成的数据。

## 测试

```bash
python -m pytest tests/ -v     # 21 passed
```

覆盖：JSON 解析容错、工具层与沙箱护栏、自愈闭环、最大轮数护栏、token 记账、
**结果校验拦住谎报**、校验通过不空耗轮数、验证器异常 fail-closed、
Trace 统计、基准集自身质量（id 唯一 / 分类合法 / expect 非空 / 任务描述含文件名）。

## 面试怎么讲（建议顺序）

1. **先讲发现**：我做了个 Coding Agent，测出它 **17%~23%** 的任务在**谎报成功**——
   而且我的判定方式是"实跑脚本验结果"，不是信它的自述。
2. **再讲解法**：把"事实判定"从人工步骤**内建成 Agent 循环里的一个环节**，
   校验不通过就把实际输出喂回去让它继续改。
3. **再讲代价与收益**：+13% token，换幻觉率 **−75%**、成功率 **+10~16pt**。
4. **再讲实验严谨性**：温度 0.2 仍有随机性，所以跑两遍报区间，并指出
   DeepSeek-V3 那组的耗时离群**不能直接横向比**。
5. **最后讲边界**：`logic` 类是天花板，原因是模型的"最小改动倾向"；
   校验器只能告诉它"不对"，告诉不了它"你为什么想错了"。
