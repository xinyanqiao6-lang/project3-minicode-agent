# MiniCode · 轻量级 Coding Agent（v2）

> 在 project1 网关「韧性调用」模式之上，实现 Coding Agent 的 Planner-Action-Observation 循环，
> 并在 v2 中解决了 v1 发现的**幻觉式汇报**问题：把「用事实判定」这条原则内建进 Agent 循环。

## 核心结论（30 个 bug 用例 × 2 次独立实测，见 `results/eval_*.md`）

| 配置 | 自愈成功率 | **幻觉式汇报率** | 平均轮数 | 平均 token/任务 |
|---|---|---|---|---|
| v1 行为（无结果校验） | **77%**（两次一致） | **17% ~ 23%** | 4.20 ~ 4.37 | 2912 ~ 3184 |
| **v2（启用结果校验）** | **87% ~ 93%** | **3% ~ 7%** | 4.40 ~ 4.63 | 3329 ~ 3483 |

**为什么给区间而不是单个数字**：模型温度已调到 0.2，但输出仍不确定。
所以 A/B 各跑了两遍（每遍 30 例），报区间而不是挑一个好看的数——
报单点数字在面试里经不起"你跑了几次"的追问。

**代价**：平均多 0.2~0.4 轮、多 ~400 token（+13%）。
**收益**：幻觉率下降约 **16 个百分点（降幅约 75%）**，成功率提升 **10~16 个百分点**。

## v2 做了什么

### 1. 结果校验步骤（核心改进）

v1 的实测发现：**5 个 case 里有 2 个，Agent 全程没报失败，最后宣称"已修复"，但实际没修对。**
也就是 40% 的幻觉式汇报率。v1 只能靠人工事后判定，Agent 自己完全不知情。

v2 把"用事实判定"内建进 Agent 循环：

```
模型想输出 final
     │
     ├─ v1：直接采信 ← 幻觉的来源
     │
     └─ v2：先验事实
          ├─ verifier 通过 → 采信 final
          └─ verifier 不通过 → 把「实际输出 vs 期望输出」喂回模型 → 继续修
```

关键设计：

- **verifier 与评测器分离**：循环内的 verifier 负责"给它反馈让它自愈"；
  循环结束后的独立 judge 负责"统计成功率与幻觉率"。两者独立，**避免自己判自己及格**。
- **fail-closed**：verifier 自身抛异常时按"未通过"处理，绝不放行
  （见 `test_verifier_exception_does_not_crash`）。
- **不用 `success` 当真相**：`AgentResult` 上刻意**不提供** `hallucinated` 属性。
  Agent 没有独立于自己的判定器，不可能知道事实真相——真相只由评测器给出。
  （这个设计避免了"用 success 自证清白"的循环论证。）

### 2. 基准集从 5 例扩到 30 例

v1 只有 5 个 case，样本量太小，任何结论都是观察性的。v2 按难度分 5 类各 6 例：

| 类别 | 说明 | 例数 |
|---|---|---|
| `syntax` | 语法错误——stderr 直接指明，最容易 | 6 |
| `runtime` | 运行时异常——需正确理解异常信息 | 6 |
| `logic` | **逻辑错误（不报错但结果错）**——最考验意图理解 | 6 |
| `dependency` | 依赖/接口错误——调用不存在或用错 API | 6 |
| `boundary` | 边界条件——空、除零、负数、极端输入 | 6 |

### 3. Trace + token 成本记账

`app/trace.py` 记录每一步的 action / 参数 / 耗时 / token / 观察结果，
评测器为每个用例自动落 trace 到 `results/traces/`。
没有 trace，"它为什么修错了"永远说不清；没有 token 记账，"换个模型划不划算"无法回答。

## 分维度结论：样本太小，只用于定位，不用于下结论

> ⚠️ **先读这条**：基准集**每类只有 6 例**，±1 例就等于 ±17 个百分点。
> 所以下面这张表**不进简历、不进口头结论**，只用来看"问题大概在哪一类"。
> 简历与面试只引用聚合指标（成功率 77% → 87%、幻觉率 17%~23% → 3%~7%）。

| 类别 | A：无校验（两遍） | B：启用校验 | 关键观察 |
|---|---|---|---|
| `syntax` | 83% ~ 100% | 83% | stderr 已经把答案写脸上，校验器帮不上忙 |
| `runtime` | 50% / 50% | **100%** | 两遍 A 都是最低，B 全部修对——方向一致 |
| `logic` | 50% / 83% | **100%** | 同类两遍差 33pt，说明这格本身就不稳 |
| `dependency` | 83% / 67% | **100%** | 校验器几乎能兜住这一类 |
| `boundary` | 100% / 100% | 50% ⚠️ | **这一格不可信，见下** |

数据来源：`results/eval_20261008_005243.md`（A 第 1 遍）、`results/eval_20261008_111841.md`
与 `..._112034.md`（A 第 2 遍 + B）、`..._112209.md`（DeepSeek）；
逐例原始记录见 `results/records_*.jsonl`。

### ⚠️ `boundary` 从 100% 掉到 50%：这是数据质量问题，不是结论

B 组 6 个 `boundary` 用例**全部**呈现同一种异常形态：

| 用例 | 轮数 | 宣称完成 | 校验打回 | 错误 |
|---|---|---|---|---|
| 全部 6 例 | **1** | **False** | 0 | 无 |

对照 A 组同样 6 例：轮数 3~4、`claimed=True`、6/6 成功。

"**1 轮就结束 + 没有宣称完成 + 没有任何错误**"这三种特征同时出现，
最合理的解释是**上游返回时就已经出了问题**（空响应 / 静默截断），
而不是"校验步骤把边界题改差了"——校验只在模型**宣称完成**时才被触发，
`verify_rejected=0` 说明它这一轮根本没被调用过。

旁证：同一轮运行里还有一条 `elapsed_s ≈ 37100s`（10.3 小时）的休眠记录，
说明这一轮的执行环境本身就不干净。

**处理方式**：这一格数字不进任何结论；同时"1 轮 + 未宣称完成 + 无错误"
已被判定为**可疑记录**，不应混进统计（干净的一轮复跑才能定论）。

### 站得住的观察

在承认上述限制之后，仍有一条机制清楚、两遍方向一致的结论：

**校验器能救的是"运行时报错、但把语义改错了"的那一类**——
`runtime` 两遍 A 都是 50%，启用校验后 100%；`dependency` 从 67%~83% 到 100%。
机制是校验器能拿实际输出与期望输出比对，把"报错消掉了但结果不对"挡回去。

反过来，`logic`（不报错、但结果错）在四个数据组里的取值是
50% / 83% / 100% / **33%**——**摆动幅度横跨 67 个百分点**，
说明它在 n=6 的样本下主要由运行噪声主导，**不能下"这一类更难"的结论**。
（DeepSeek-V3 的表现正好相反：`syntax`/`runtime`/`dependency`/`boundary` 四类全对，
唯独 `logic` 只有 33%，是它唯一的短板——同一类别在不同模型上一高一低，
更说明单格数字不可当结论用。）

## 跨模型对比：模型能力是 Agent 的上限

同一套 30 例基准、同一套 harness（均启用结果校验）：

| 模型 | 成功率 | 幻觉率 | 宣称完成率 | 平均轮数 | 平均 token | **耗时中位数** |
|---|---|---|---|---|---|---|
| `Qwen/Qwen2.5-7B-Instruct` | 87% ~ 93% | 3% ~ 7% | 100% | 4.4 ~ 4.6 | 3329 ~ 3483 | **6.2s** |
| `deepseek-ai/DeepSeek-V3` | 87% | **0%** | 80% | 4.6 | 4483 | **17.6s** |

> 耗时一律用**中位数**。两组数据里各有一条 `elapsed_s ≈ 37100s`（10.3 小时）的记录，
> 是机器休眠被计入计时器造成的，会把均值抬到 1247s / 1255s 这种没有意义的数字上。
> 剔除该离群点后的均值是 10.4s / 18.2s，中位数 6.2s / 17.6s——三个口径里中位数最稳，
> 故以中位数报数。**用均值报耗时是这个项目踩过的坑之一，不要在别处重犯。**

两个值得讲的发现：

1. **DeepSeek-V3 的幻觉率为 0%，且"宣称完成率"只有 80%**——
   剩下 20% 它**没有假装完成**，而是跑满轮数后如实报告未完成。
   这说明"诚实度"不只取决于校验器，也取决于模型本身的行为倾向。
2. **DeepSeek-V3 耗时中位数 17.6s，约为 7B（6.2s）的 2.8 倍**，
   同口径下属于"更强但更慢"的正常取舍，**不构成数量级差异**。
   （先前此处误写为"平均 1255s、慢两个数量级"，那是把休眠离群点带进了均值——
   同一个错误在本项目里出现过两次，说明"耗时只报中位数"必须当成硬规则执行。）
3. **两种模型失败在完全不同的维度上**，这是比成功率更有信息量的一点：

   | 模型 | 失败用例分布 |
   |---|---|
   | Qwen2.5-7B-Instruct | `syntax` 1 例、`boundary` 3 例 |
   | DeepSeek-V3 | **`logic` 4 例**（其余类别全对） |

   DeepSeek-V3 把"语法与边界"两类全修对了，却稳定栽在 `logic`（代码能跑、结果错）上；
   7B 反过来，`logic` 能过、`syntax` 会错。也就是说：
   **`logic` 不是"模型不够强"的问题，而是"校验器能说不对、说不出为什么错"的问题**——
   换更强的模型并不能直接解决它。

## 怎么跑

```bash
python -m eval.runner --ab                             # A/B 对照（开关结果校验）
python -m eval.runner --models deepseek-ai/DeepSeek-V3 # 跨模型对比
python -m eval.runner --per-category 1                  # 每类 1 例快速冒烟
python -m eval.runner --models X --no-verify           # 复现 v1 行为
```

结果写入 `results/eval_<时间戳>.{md,json}`，逐例 trace 写入 `results/traces/`。
评测带**断点续跑**（每例结果实时落 jsonl），中断不会丢已完成的数据。

```bash
python -m pytest tests/ -v     # 21 passed
```

## 面试怎么讲（建议顺序）

1. **先讲发现**：我做了个 Coding Agent，测出它 **17%~23%** 的任务在**谎报成功**——
   而且我的判定方式是"实跑脚本验结果"，不是信它的自述。
2. **再讲解法**：把"事实判定"从人工步骤**内建成 Agent 循环里的一个环节**，
   校验不通过就把实际输出喂回去让它继续改。
3. **再讲代价与收益**：+13% token，换幻觉率 **−75%**、成功率 **+10~16pt**。
4. **再讲实验严谨性**：温度 0.2 仍有随机性，所以跑两遍报区间，并指出
   DeepSeek-V3 那组的耗时离群**不能直接横向比**。
5. **最后讲边界**：`logic` 类是天花板，原因是模型的"最小改动倾向"；
   校验器只能告诉它"不对"，告诉不了它"你为什么想错了"。
